# Command Center Companion

Version `0.5.0` adds the application automation bridge. A background service worker polls the workspace for queued automation runs (every minute, `alarms`), opens the job URL in a background tab, and executes a served site adapter (`greenhouse.yaml`) through a separate `adapter-runner.js` content script. The worker operates **only** on origins pre-granted in **Automation sites** (Capture settings area): grants happen only from that explicit user gesture, the background never requests permissions, and an ungranted origin fails the run with `origin_not_authorized`. Runs record per-field DOM-structural evidence — never screenshots — and end in `ready_for_review`. The companion never clicks Next or Submit; an application reaches `submitted` only after explicit workspace authorization stamps `submit_authorized_at`, and the adapter's Simplify handoff treats non-detection as a success-path no-op. All run state lives in `chrome.storage.local`, so a service-worker death recovers on the next alarm tick.

Companion `0.4.8` fixes capture from a side panel that stays open across tabs. It reads the selected tab's URL with the `tabs` permission and requests access only to that site's origin when you select Autofill or Share this form. Allow Chrome's site-access prompt to continue. Denied access and a changed active page stop capture with a recovery message. Optional website access is not granted to every site at installation.

The installed `0.4.8` companion was verified in an existing Chrome session on a live Coframe Ashby application: four profile fields filled and the selected résumé attached. The searchable location dropdown and an unanswered onsite/relocation question remained manual. This application was not submitted. Fifty synthetic browser regressions also pass; this evidence does not establish coverage of every ATS.

Version `0.4.7` added entry into the same Ashby posting's Application tab from Overview, captures its Yes/No button groups, and shows actionable failures beside Autofill. Choice filling updates the site's state, preserves existing or edited answers, rejects changed controls, and prevents native form submission. Reload the unpacked extension and refresh the job page after updating. The public Ashby form was inspected live; filling and recovery were verified with synthetic browser fixtures, not a submitted employer application.

**This browser** remains the default for new installations. It reads the Chrome tab where you opened the extension and retains bounded employment/education row creation and recognized job continuity across supported application pages.

Autofill uses active reviewed candidate facts. Uploading or selecting a résumé does not approve its contents as profile facts. Review source-linked proposals in Settings → Reviewed candidate facts, then use **Generate grounded drafts** for written questions and review the answers before filling. Missing eligibility or other personal answers remain questions. Broader authenticated ATS coverage and complete Simplify parity are unverified.

If capture fails, open **Capture settings** and choose **This browser (recommended)**. An explicitly saved AgentBrowser preference is preserved across upgrades; that advanced mode needs its separate native helper and browser. Select the application tab, press Autofill and allow access to its site if Chrome asks. Chrome settings, extension pages, and the Chrome Web Store cannot be captured.

Start the API on localhost:8000 and web app on localhost:3001. In Chrome's Extensions page, enable Developer mode and Load unpacked → this directory. Open the workspace's Browser companion page, create a pairing code, and paste it into the extension popup.

Open an application form and click **Share this form**. The popup can prepare reviewed profile answers, keep local edits across popup closes, queue grounded draft generation, pin an exact resume version, and create a fill proposal. Choose every resume upload control explicitly. Click **Check fill proposals**, review every answer and file, then apply. Pairing codes are one-use and expire in five minutes; device credentials can be revoked in the workspace. Extension storage is restricted to trusted extension contexts and holds the revocable device credential plus the current local review draft.

The companion supports native text/email/telephone/URL and numeric inputs, textareas, single selects, radio groups, checkboxes, and explicitly selected file inputs in the main document and visible same-origin application frames. Frame document identity and its full URL remain local; reloading or replacing a frame invalidates its captured fields. Hidden, captcha and cross-origin frames are excluded. Associated visually hidden file inputs are supported. Numeric answers must satisfy the captured range and step in both the domain model and the browser.

Bounded Greenhouse-style single-select widgets expose their exact options for review. The companion verifies the complete option list before applying and confirms the site's selected state afterward. It handles up to 300 choices; duplicate, asynchronous/search-only, multi-select and unknown widgets remain manual. Lever location suggestions remain manual because display text alone does not establish its canonical selection. Ashby-native controls update React state, and the real Resume input is selected separately from Autofill from resume. Career date/month controls use only known source precision and retain range/step checks. Rich text editors, inaccessible controls and sensitive password/payment/SSN fields are excluded or disclosed as unsupported.

Capture records only whether an existing value is present, never that value. Existing values require explicit replacement; edits made after capture are always preserved and need a fresh share/review. Exact resume bytes are downloaded only after claim, verified by size and SHA-256 in the popup and content script, and attached through `File` and `DataTransfer`.

In `0.4.4`, **Autofill this page** can add employment/education rows through explicit Add buttons in unambiguous empty history sections. Saved preparation targets count up to ten distinct approved unscoped entries per kind; ambiguous chronology yields zero. Existing values and ambiguous controls remain manual. The row-operation ID survives retries so interrupted requests do not double-add. A rerendered Add button is accepted only after a new row is confirmed and its history kind, label and section scope still match. Expansion is followed by a fresh capture and preparation under the same application before filling. A history-only page can begin with zero fields; AgentBrowser requires a valid local Add hint for that capture. The local `InspectResult.history_expandable` marker is omitted from API payloads.

The companion never clicks Next or Submit. A proposal is tied to the exact live URL and captured control structure; stale pages require a fresh share. Each field reports filled, uploaded, preserved, unsupported, rejected, failed, or outcome unknown. A claimed command is recorded locally before apply and never replayed automatically, including when the page or result endpoint becomes unavailable.

Synthetic browser coverage includes grouped controls, uploads, numeric constraints, same-origin frames, React state and bounded custom selection. All fixture data is fictional. Hands-on verification across Greenhouse, Lever, Ashby, Workday and iCIMS is deferred to the user; no signed-in employer form or real application submission is claimed. Sign in and open the desired application step before sharing; a Workday login gate is not a fillable form. Remote API deployments need an explicit host-permission and HTTPS configuration change.

HTTP payloads and the versioned popup/content messages are defined in `apps/api/src/command_center/api/browser_contracts.py`. Run `make contracts` after schema changes; this generates Next.js types and the bundled `contracts.js` runtime validators. Both sides reject incompatible/malformed messages before filling. Validators are compiled ahead of time for Manifest V3 (no eval or remote code). Reload the unpacked extension and the application tab after updates. `make contracts-check` catches drift and `make test-browser` starts its own synthetic fixture server on port 4319.

In `0.4.5`, supported Greenhouse, Lever, Ashby, Workday and iCIMS posting URLs provide a saved job identity. A matching current application continues across pages; a different recognized posting starts a new application. Unknown pages retain the Continue/New choice. Both reader modes use the same fixed parser; Direct browser is labelled separately from AgentBrowser. Canonical posting links omit tracking/session query data. Version `0.4.7` can enter an Ashby posting's Application tab from Overview; Next and Submit remain manual.
